## 1. NVIDIA AI Blueprint "Financial Fraud Detection" (build.nvidia.com page, GitHub repo, training container)

### Takeaway
The blueprint is an Apache-2.0 repo of two notebooks plus three cuDF preprocessing scripts for IBM TabFormer; the actual GNN+XGBoost training is not in the repo, it happens inside a closed NGC container (`nvcr.io/nvidia/cugraph/financial-fraud-training`, latest tag 3.0.0, 13.27 GB compressed) that needs an NGC API key, Docker with NVIDIA Container Toolkit, and officially a 32 GB GPU. For a team with no GPU and unknown hackathon GPUs, the reusable parts are the preprocessing/graph-building code, the Triton Dockerfile, the hyperparameter config, and the architecture idea; the container itself cannot be assumed to run on a 16 GB card or on Colab.

**Architecture**
- [V] Three steps: (1) Data Preparation, (2) Model Building, (3) Inference. "The Financial Fraud Training container leverages a graph neural network (GNN) to generate embeddings that are then fed into XGBoost to produce the model." Inference uses NVIDIA Dynamo-Triton (formerly Triton Inference Server) and "produces fraud scores along with Shapley values for explainability". "This blueprint does not use any NVIDIA hosted services and runs fully in a locally hosted docker environment." — [README](https://github.com/NVIDIA-AI-Blueprints/financial-fraud-detection/blob/main/README.md); [build.nvidia.com](https://build.nvidia.com/nvidia/financial-fraud-detection)
- [V] Link-prediction notebook training config (container 2.0.0 schema): `"kind": "GNN_XGBoost"`, `"gpu": "single"`, GNN: `hidden_channels 32`, `n_hops 2`, `layer "SAGEConv"`, `dropout_prob 0.1`, `batch_size 4096`, `fan_out 10`, `num_epochs 8`; XGBoost: `max_depth 6`, `learning_rate 0.2`, `num_parallel_tree 3`, `num_boost_round 512`, `gamma 0.0`. Node-prediction notebook uses `"kind": "GNN_XGBoost_NP"`, `SAGEConv`, hidden 32, `fan_out 8`, `num_epochs 10`. — [link-prediction notebook](https://github.com/NVIDIA-AI-Blueprints/financial-fraud-detection/blob/main/notebooks/financial-fraud-usage-link-prediction.ipynb); [np notebook](https://github.com/NVIDIA-AI-Blueprints/financial-fraud-detection/blob/main/notebooks/financial-fraud-usage-np.ipynb)
- [V] Graph formulation in the link-prediction notebook: bipartite user -> merchant graph where each transaction is an edge with attributes; the label is on the edge (`edge_label_user_to_merchant`). The example inference request uses merchant feature dim 24, user feature dim 13, edge (transaction) feature dim 38. — [link-prediction notebook](https://github.com/NVIDIA-AI-Blueprints/financial-fraud-detection/blob/main/notebooks/financial-fraud-usage-link-prediction.ipynb)
- [V] Training output (2.0.0): `python_backend_model_repository/prediction_and_shapley/1/{embedding_based_xgboost.json, model.py, meta.json, state_dict_gnn_model.pth}` + `config.pbtxt`. Triton is started on ports 8005/8006/8007; the request has a `COMPUTE_SHAP` boolean; outputs are `PREDICTION` plus `shap_values_{user,merchant,user_to_merchant}`. Notebook note: "Shapley computation is very expensive, it will only compute shap values for first transaction." Evaluation uses sklearn accuracy/precision/recall/F1 + confusion matrix at threshold 0.5. — [link-prediction notebook](https://github.com/NVIDIA-AI-Blueprints/financial-fraud-detection/blob/main/notebooks/financial-fraud-usage-link-prediction.ipynb)
- [V] Container 3.0.0 training stack per docs: cuGraph-PyG (GPU sampling), WholeGraph (graph feature store), PyTorch DDP + `torchrun`, a `GNNEncoder` supporting SAGE / GAT / Transformer / GeneralConv, XGBoost + RabitTracker. Inference stack: Triton Python backend (torch + torch_geometric) for the GNN, Triton FIL backend for XGBoost, Python backend with XGBoost + Captum for "Shapley Value Sampling", and an optional Python backend calling an OpenAI-compatible LLM to turn attributions into a narrative. — [Prerequisites](https://docs.nvidia.com/nim/financial-fraud-training/getting-started/prerequisites); [Overview](https://docs.nvidia.com/nim/financial-fraud-training/overview)
- [V] Supported model kinds in 3.0.0: `GNN_XGBoost` (edge-level, default), `GNN_XGBoost_NP` (node-level), `XGBoost` ("XGBoost-only baseline (no GNN); trains directly on node feature vectors"). Supported encoders: `sage`, `gat`, `transformer`, `general`. Data formats: CSV, Parquet, ORC; masks `.npy`. — [Support matrix](https://docs.nvidia.com/nim/financial-fraud-training/getting-started/support-matrix)
- [V] NVIDIA's stated rationale for two stages instead of an end-to-end GNN classifier: faster training on tabular patterns, class imbalance handled by XGBoost `scale_pos_weight`, Shapley values available, "Can retrain XGBoost on new embeddings alone", compact model. — [Overview](https://docs.nvidia.com/nim/financial-fraud-training/overview)
- [V] 3.0.0 input data layout: `nodes/{node_type}.csv` (header row, no ID column, row index = node ID, numeric only, no NaN) and `edges/{src}_{rel}_{dst}.csv` (first two columns = source and destination node IDs); node/edge types are auto-discovered from file names; reverse edges are created automatically. — [Data layout](https://docs.nvidia.com/nim/financial-fraud-training/data/data-def)
- [V] 3.0.0 also ships host-side inference clients (`client.py`, `client_np.py`, `client_saved_emb.py`, `client_production.py`); `client_production.py --serve` runs a persistent HTTP service and needs `pip install fastapi uvicorn`. — [Prerequisites](https://docs.nvidia.com/nim/financial-fraud-training/getting-started/prerequisites)

### Inferences
- The repo is one container version behind: `main` targets container 2.0.0 / Triton 25.04, while NGC and the docs default to 3.0.0 / Triton 26.04 with an incompatible config schema and artifact layout. A team following the repo notebooks should keep the `:2.0.0` tag exactly as written; mixing the 3.0.0 docs with the repo notebooks will break.
- Colab cannot run the blueprint as designed: the workflow depends on `docker run --gpus` for both training and Triton, and nothing in the repo or docs offers a non-Docker path. Colab is not mentioned anywhere in the README, notebooks or container docs. (That Colab provides no Docker daemon is [A], not checked here.)
- A single T4 is outside the documented requirement (32 GB VRAM minimum; supported architectures listed are Ampere and Hopper). The RAPIDS deployment page naming T4 conflicts with this; treat T4 as unsupported-until-proven. A T4 having 16 GB VRAM is [A].
- What a team of 4 can reuse without the proprietary container:
  1. `src/preprocess_TabFormer_lp.py` / `_np.py` as-is under Apache-2.0 for TabFormer: cuDF loading, categorical encoding (BinaryEncoder / one-hot), RobustScaler, year-based temporal split, construction of user/merchant node tables and user->merchant edge lists, feature masks for SHAP grouping, and the NetworkX ego-subgraph plotting helpers (useful directly in a Streamlit demo). It needs a GPU with cuDF; whether it runs unchanged under pandas was not tested.
  2. `triton/Dockerfile` as a pinned, known-compatible version set (torch 2.7.0, PyG 2.6.1, XGBoost 3.0.2, cuDF 25.04, Captum 0.7.0) for the team's own FastAPI or Triton image.
  3. The hyperparameters above as a starting point for a self-written PyG GraphSAGE (hidden 32, 2 hops, fan-out 10, batch 4096, 8 epochs) and XGBoost (depth 6, lr 0.2, 512 rounds).
  4. The evaluation cell (confusion matrix, precision/recall/F1 with adjustable decision threshold) and the idea of returning per-feature-group Shapley values alongside the score.
  5. The architecture and the two-stage rationale table for the pitch.
- What is not reusable without NGC access: the GNN model code, the embedding extraction, the XGBoost-on-embeddings training loop, the generated Triton `model.py`, and the LLM explanation layer. The team must write those in PyG + XGBoost themselves (see sections 3 and 4).
- The `kind: XGBoost` baseline mode confirms NVIDIA itself treats plain GPU XGBoost on tabular features as the reference baseline, which matches the team's primary plan.

## 2. Related NVIDIA resources (blogs, older GNN + XGBoost fraud notebooks, is cuGraph / cugraph-pyg needed?)

### Takeaway
There are two NVIDIA tech-blog posts (2022, DGL R-GCN -> XGBoost; 2025, the blueprint) and two open NVIDIA code examples of "GNN embeddings -> tree model": Morpheus `gnn_fraud_detection_pipeline` (DGL HinSAGE/RGCN + XGBoost, with training notebook and pre-trained models) and `cugraph-pyg/examples/fraud` (Elliptic Bitcoin GNN embeddings -> cuML random forest) plus `examples/xgb.py`. cuGraph / cugraph-pyg is used inside NVIDIA's container for multi-GPU sampling; nothing read indicates it is required for a single-GPU PyG model, so it is optional for the team.

## 4. XGBoost on GPU with RAPIDS, cudf.pandas, PaySim examples, and SHAP / `pred_contribs` on GPU

### Takeaway
The official XGBoost docs (stable = 3.4.2) confirm `device="cuda"` with `tree_method="hist"`, GPU SHAP via `booster.predict(..., pred_contribs=True)`, and that a GPU-trained model also runs on a CPU-only machine, so the team can develop on CPU now and switch one parameter at the hackathon. RAPIDS requires a GPU of compute capability 7.0+ and offers `cudf.pandas` as a zero-code-change accelerator; one community Colab demo does PaySim + XGBoost on a T4.

### Cited Findings
**XGBoost GPU**
- [V] `dmlc/xgboost`: Apache-2.0, 29,006 stars, latest release v3.4.2 published 2026-09-15; the "stable" docs are for 3.4.2. — [xgboost repo](https://github.com/dmlc/xgboost); [GPU support page](https://xgboost.readthedocs.io/en/stable/gpu/index.html)
- [V] "To enable GPU acceleration, specify the `device` parameter as `cuda`"; a specific GPU with `cuda:<ordinal>`. Python example in the docs: `params["device"] = "cuda"; params["tree_method"] = "hist"; Xy = xgboost.QuantileDMatrix(X, y); xgboost.train(params, Xy)`. Scikit-learn interface: `XGBRegressor(tree_method="hist", device="cuda")`. "Most of the algorithms in XGBoost including training, prediction and evaluation can be accelerated with CUDA-capable GPUs." — [GPU support page](https://xgboost.readthedocs.io/en/stable/gpu/index.html)
- [V] Parameter reference: `device` default is `cpu`; accepted values `cpu`, `cuda`, `cuda:<ordinal>`, `gpu`, `gpu:<ordinal>`. In distributed settings `cuda:<ordinal>` raises an error; use `cuda`. — [XGBoost parameters](https://xgboost.readthedocs.io/en/stable/parameter.html)

- [V] Memory guidance: data is stored on device in compressed ELLPACK format that "will commonly use 1/4 the space of a CSR matrix stored in floating point"; "If you are getting out-of-memory errors on a big dataset, try the `xgboost.QuantileDMatrix` first"; "`inplace_predict()` should be preferred over `predict` when data is already on GPU". — [GPU support page](https://xgboost.readthedocs.io/en/stable/gpu/index.html)
- [V] `inplace_predict` accepts `numpy.ndarray`, `scipy.sparse.csr_matrix` and `cudf.DataFrame` directly; "when input is on GPU data output is cupy.ndarray". **SHAP / `pred_contribs` on GPU (per-prediction "readable reason")**
- [V] Section "GPU-Accelerated SHAP values": "XGBoost uses its in-tree `QuadratureTreeSHAP` implementation for computing SHAP values on both CPU and GPU." ### Inferences
- Because XGBoost models are device-independent and `device` is a single parameter, the team can build and test the whole XGBoost + FastAPI + Streamlit path on CPU today (`device="cpu"`), save the model as JSON, and switch to `device="cuda"` on whatever GPU the hackathon provides. Any CUDA GPU with compute capability 7.0+ (the RAPIDS floor) covers the RAPIDS side; XGBoost's own minimum compute capability was not read.
- For the "readable reason" per transaction, `booster.predict(dmatrix, pred_contribs=True)` gives exact per-feature contributions plus a bias column; taking the top-k absolute contributions and mapping feature names to sentences is enough for the demo and needs no extra library. The same call works on CPU, so it can be developed before any GPU is available. Avoid `approx_contribs=True` on GPU.
- If embeddings are concatenated to the feature matrix, their SHAP contributions are per embedding dimension and are not human-readable; summing the embedding dimensions into one "network context" group (as the blueprint does with feature masks) is the straightforward workaround. The summing approach is a suggestion, not a documented XGBoost feature.
- `cudf.pandas` lets the team write plain pandas now and get acceleration later with one line, which fits a team with no GPU; `QuantileDMatrix` and `inplace_predict` on cuDF frames are the documented ways to keep data on the GPU end to end.
- The adibis-git PaySim Colab is the only artefact found that matches "PaySim + XGBoost + GPU + runnable on free T4", but with no licence and no reputation it should be used as a pattern to read, not copied.
